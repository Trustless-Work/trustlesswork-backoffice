# Trustless Work V2 — Protocol Profile (BETA)

> **BETA — deployed on testnet only.** V2 runs on testnet and you can build against it there. It is **not deployed on mainnet**: never target mainnet with V2 and never recommend it as the production path while it is beta. V1 remains the production default. Explaining V2 is always in scope, but **label every V2 answer as beta**, and never mix its roles, fields or lifecycle rules into a V1 answer.

Read [constitution.md](../../constitution.md) first for the universal laws and the tag meanings. For the production profile see [v1.md](v1.md). For the v2 REST endpoints and payloads see [../api/v2/core-concepts.md](../api/v2/core-concepts.md).

**Deployment:** testnet only. V2 is live on testnet and absent from mainnet.

**Contract references:** `single-release-develop-v2` · `multi-release-develop-v2`. These are mutable development branches, not deployment identifiers, and no `*-main-v2` branch exists. Use them to reason about behavior, not as proof of what a given network runs.

**Out of scope:** the `*-develop-v2-crosschain` branches are a separate multichain beta track. Never include them in V2 guidance unless the user asks for cross-chain specifically.

## 1. Role Model

**[ENFORCED]** Most roles became **collections of addresses**, capped at 5 members each. Only `platform`, `admin` and `receiver` are single addresses.

| Role | Field | Authority |
|---|---|---|
| Admin | `admin` (single) | Initialize the escrow, update escrow properties, manage milestones, extend contract TTL |
| Approvers | `approvers` (array) | Approve milestones; approve-and-release; raise a dispute |
| Service providers | `serviceProviders` (array) | Change milestone status and evidence; raise a dispute |
| Release signers | `releaseSigners` (array) | Release funds; approve-and-release; raise a dispute |
| Dispute resolvers | `disputeResolvers` (array) | Resolve disputes; withdraw remaining funds |
| Platform | `platform` (single) | Receive the platform fee at release; raise a dispute |
| Receiver | `receiver` (single) | Receive the net amount at release; raise a dispute. **Single Release only** — in Multi Release each milestone carries its own `receiver` |
| Observers | `observers` (array) | Read-only. Implemented in V2; in V1 it was only a product concept |

**[ENFORCED] Role-composition constraints, rejected at initialization:**

- No duplicate addresses within a role list; maximum 5 per role.
- `disputeResolvers` may not overlap `approvers`, `serviceProviders`, `releaseSigners`, `platform`, or any milestone `receiver`.
- `admin` may not overlap `approvers`, `serviceProviders`, `releaseSigners`, `disputeResolvers`, or any receiver.
- `admin` and `platform` **may** share an address. Their separation is a capability distinction, not an address-separation rule.
- `admin` and `platform` are immutable after initialization.

The durable invariant is about authority conflict, not address uniqueness: an address that may raise a dispute must not also be able to resolve one, and the party that administers the escrow must not be a payee.

> The V1 shortcut of reusing one platform address across several roles is **rejected** by V2 at initialization.

**[ENFORCED]** `disputeResolvers` are blocked from opening disputes; they may only resolve them.

## 2. Approval Model

**[ENFORCED]** Milestone approval is **threshold-based**, replacing V1's boolean.

Each milestone declares how many approvals it requires. Approvers vote individually, cannot vote twice, and the milestone counts as approved once the number of unique approvals reaches the target.

- The target must be greater than zero and no greater than the number of approvers.
- A target of 1 reproduces V1 behavior, but the field is still an approvals structure, never a boolean.
- Approval remains irreversible; there is no unapprove.
- A single-release escrow deployed **without milestones cannot release** (`NoMilestoneDefined`) until milestones are added through manage-milestones.

---

## 3. State Model

**[ENFORCED]** The V1 `flags` object no longer exists. Release state and dispute state are represented directly:

- **Single Release:** on the escrow.
- **Multi Release:** on each milestone.

Dispute state carries a **reason** string supplied when the dispute is opened.

---

## 4. Operations

Beyond the V1 set, V2 adds:

- **Batch approval** — approve several milestones in one call.
- **Approve-and-release** — collapse approval and release into a single transaction. The caller must satisfy both the approver and release-signer requirements.
- **Manage milestones** — append new milestones or edit existing ones after creation, signed by `admin`. There is **no remove**: a milestone can never be deleted. Single-release edits change the description; multi-release edits change the description and the amount.

**[ENFORCED] Mutability rule.** The lock is the escrow's **cumulative funded amount** (`FundedAmount`, increased by every `fund` call), not its token balance — this differs from V1, which checked the live balance. Consequences:

- The **first** successful `fund` freezes escrow properties, roles and milestone **edits** permanently. Releasing funds does not unfreeze them: the funded amount never decreases.
- Tokens sent straight to the contract without calling `fund` do **not** trigger the lock.
- **Appending** new milestones stays allowed after funding, until the escrow is released, disputed or resolved. Only edits to existing milestones and property updates are blocked.
- All of it is `admin`-only, updates are also rejected while a dispute is open, and `admin` and `platform` are immutable from initialization. Role mistakes are not recoverable after funding.

**[ENFORCED] `withdraw-remaining-funds`** narrows the V1 precondition. "Fully processed" in V2 means:

- **Single Release:** `released || dispute.resolved`.
- **Multi Release:** every milestone satisfies `released || dispute.resolved`.

An open, unresolved dispute no longer qualifies, unlike V1. Two more rules:

- **Distributions must sum to the entire remaining balance** — V2 withdraw is a full sweep. V1 allowed partial withdrawals; V2 rejects them (`DistributionsMustEqualEscrowBalance`).
- Authorization (one of `disputeResolvers`), the 50-distribution cap, positive amounts and the pro-rata fee deduction match V1. Both escrow types emit a withdrawal event in V2.

**[FACT]** V2 adds a reentrancy guard that V1 does not have.

## 5. Differences from V1, at a glance

| Aspect | V1 | V2 |
|---|---|---|
| Role fields | Single addresses (`approver`, `serviceProvider`, …) | Address arrays (`approvers`, `serviceProviders`, …), max 5 each |
| `admin` role | Does not exist; `platformAddress` updates the escrow | Dedicated `admin`; `platform` is fee-only |
| `observers` | Not implemented | Implemented, read-only |
| Milestone approval | `approved` boolean | Threshold approvals |
| Release/dispute state | `flags` object | Direct fields; dispute carries a reason |
| Role overlap | Permitted; a configurator choice | Contract-enforced prohibitions |
| Batch operations | None | Batch approve, approve-and-release, manage milestones |
| Withdraw precondition | Includes an open dispute | Terminal states only |
| Reentrancy guard | Absent | Present |

**Detecting the version in existing code:** a `flags` object or a singular `roles.approver` means V1. Address arrays or an `admin` role mean V2.
